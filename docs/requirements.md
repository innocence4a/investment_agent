- 作成日: 2026-07-10
- ステータス: ドラフト(発注者確認待ち)
- 参照元: https://x.com/robrtcode/status/2064361958392938550

## 1. 目的・ゴール

AI エージェント(LLM)が市場情報を収集・分析し、あらかじめ定義した投資ロジックとリスク制約の範囲内で、証券会社の API を通じて自動的に売買・ポートフォリオ管理を行うシステムを構築する。

**ゴール(段階的)**
1. Phase 1: ペーパートレード(仮想売買)で 1 ヶ月以上安定稼働し、判断ログが人間にレビュー可能であること
2. Phase 2: 少額実資金(上限額は別途決定)で自動売買が行えること
3. Phase 3: 運用額の段階的拡大(Phase 2 の実績評価後に判断)

## 2. スコープ

### 対象(In Scope)
- 市場データ・ニュースの自動収集
- LLM による分析・売買判断(判断根拠の記録を含む)
- 証券会社 API/MCP 経由の発注・約定確認・ポジション管理
- リスク管理(損切り・上限額・取引頻度制限などのハードガードレール)
- 通知・レポーティング(取引実行時、異常時、日次/週次サマリ)
- ペーパートレード環境

### 対象外(Out of Scope / 別途決定事項)
- **証券会社の選定**(発注者側で決定。§9 に選定の観点のみ整理)
- **投資ロジックの決定**(発注者側で決定。§9 にロジックがシステム要件に与える影響のみ整理)
- 第三者向けサービス化(投資助言・運用業に該当するため本プロジェクトでは扱わない。自己資金・自己利用に限定)

## 3. 前提・制約

- 利用者は個人(自己資金・自己判断・自己責任での運用)
- LLM は Claude(Anthropic API)を第一候補とする
- 実行環境はクラウド(VPS またはサーバレス + スケジューラ)を想定
- 日本居住者の場合、米国系ブローカー(Robinhood 等)は口座開設不可のため、選定時に国内 API 提供業者(kabu ステーション API、立花証券 e支店 API 等)または Interactive Brokers / Alpaca 等の利用可否を確認する

## 4. システム構成(想定アーキテクチャ)

```
[スケジューラ(cron 等)]
        │ 定期起動(例: 市場開始前/中/後)
        ▼
[エージェント本体(Claude + エージェントフレームワーク)]
   ├─ ① データ収集: 株価・出来高・指標・ニュース・決算(データ API)
   ├─ ② 分析・判断: 投資ロジック(プロンプト+ルール)に基づく売買判断
   ├─ ③ リスクチェック: コード実装のハードガードレール(LLM の判断より優先)
   ├─ ④ 発注: 証券会社 API / MCP 経由
   └─ ⑤ 記録・通知: 判断根拠ログ、取引履歴 DB、Slack/LINE/メール通知
```

**設計上の決定事項(重要)**
- リスク制約(1 取引あたり上限、日次損失上限、禁止銘柄等)は **LLM のプロンプトではなくコードで強制**する。LLM が誤判断してもガードレール層で発注を拒否できる構成とする。
- すべての売買判断は「判断根拠(なぜ買う/売るか)」をテキストで残し、後から人間が監査できるようにする。
- 発注用 API キーは最小権限(可能なら「取引専用サブ口座」「出金権限なし」)で発行する。

## 5. 機能要件

| # | 機能 | 内容 | 優先度 |
|---|------|------|--------|
| F-1 | データ収集 | 対象銘柄の株価・出来高・テクニカル指標・ニュース・決算情報を定期取得 | 必須 |
| F-2 | 売買判断 | 投資ロジックに基づき LLM が「買い/売り/ホールド」と数量を決定し、根拠を出力 | 必須 |
| F-3 | ガードレール | 上限金額・損失上限・取引頻度・許可銘柄リスト等をコードで強制。違反時は発注拒否+通知 | 必須 |
| F-4 | 発注・約定管理 | 証券会社 API で発注、約定確認、失敗時のリトライ/取消 | 必須 |
| F-5 | ポジション管理 | 保有銘柄・平均取得単価・評価損益の把握。損切り/利確ラインの監視 | 必須 |
| F-6 | 記録 | 全判断・全取引・全 API 応答を DB に保存(監査・振り返り用) | 必須 |
| F-7 | 通知 | 取引実行・エラー・ガードレール発動を即時通知。日次/週次パフォーマンスレポート | 必須 |
| F-8 | ペーパートレード | 実発注せず仮想約定でロジック検証できるモード(Phase 1 で使用) | 必須 |
| F-9 | 緊急停止 | ワンアクションで全自動売買を停止できるキルスイッチ(通知からの操作を含む) | 必須 |
| F-10 | バックテスト | 過去データでロジックの成績を検証 | 推奨 |

## 6. 非機能要件

| # | 項目 | 要件 |
|---|------|------|
| N-1 | セキュリティ | API キーはシークレット管理サービスで保管(コード・リポジトリに含めない)。発注 API は出金不可権限。 |
| N-2 | 可用性 | 市場時間中の稼働率を優先。エージェント障害時は「新規発注停止」に倒す(ポジション放置リスクは通知でカバー) |
| N-3 | 監査性 | すべての判断・取引が時系列で追跡可能であること |
| N-4 | コスト | LLM API・データ API・実行環境の月額上限を設定し、超過時はアラート |
| N-5 | レイテンシ | デイトレード/スキャルピングは対象外(LLM 判断の所要時間的に不向き)。日次〜週次の判断サイクルを前提 |

## 7. 必要な準備(証券会社選定・投資ロジック決定以外)

1. **口座・API 関連**
   - 証券口座の開設と API 利用申請(審査に数日〜数週間かかる場合あり)
   - API キー発行と権限設定(取引可・出金不可)
   - ペーパートレード/デモ口座の有無確認(なければ自前で仮想約定層を実装)
2. **LLM・開発環境**
   - Anthropic API キーの取得と利用上限設定
   - 実行環境(VPS / クラウド)とスケジューラの準備
   - GitHub リポジトリ・CI(本リポジトリ)
3. **データソース**
   - 市場データ API の契約(証券会社 API に含まれるか、Yahoo Finance / J-Quants / Polygon 等を別途契約するか)
   - ニュース・決算情報のソース選定
4. **資金・運用ルール**
   - 投入資金額と「失っても許容できる上限」の決定
   - リスクパラメータの初期値決定(1 取引上限、日次損失上限、最大ポジション数)
5. **法規制・税務の確認**
   - 自己資金・自己利用の範囲であれば投資助言・運用業の登録は不要。ただし第三者の資金を扱う/シグナル配信する場合は金商法上の登録が必要になるため、スコープ外と明記
   - 証券会社の約款で自動発注(bot)が許容されているかの確認
   - 譲渡益・配当の税務処理(特定口座源泉徴収ありの利用可否。※自動売買は取引回数が増えやすい)
6. **運用体制**
   - 通知先(Slack / LINE / メール)の準備
   - 週次で人間がログ・成績をレビューする運用ルール
   - 緊急停止手順の確認(証券会社側での API 無効化を含む)

## 8. 開発フェーズとマイルストーン(目安)

| Phase | 内容 | 完了条件 | 期間目安 |
|-------|------|----------|----------|
| 0 | 要件確定・証券会社/ロジック決定・口座開設 | API キー取得完了 | 2〜4 週間 |
| 1 | ペーパートレード版実装(F-1〜F-9) | 1 ヶ月連続稼働・判断ログのレビュー完了 | 4〜6 週間 + 検証 1 ヶ月 |
| 2 | 実資金(少額)接続 | ガードレール発動テスト合格、少額での安定稼働 | 2 週間 + 検証 1 ヶ月 |
| 3 | 運用額拡大・ロジック改善(バックテスト F-10 含む) | Phase 2 の成績評価に基づき判断 | 継続 |

## 9. 別途決定事項への補足(選定の観点のみ)

### 証券会社選定の観点
- 発注 API / MCP の提供有無と安定性(国内: kabu ステーション API、立花証券 e支店 API 等。海外: Interactive Brokers、Alpaca、Robinhood(米国居住者のみ、MCP 対応))
- ペーパートレード環境の有無
- 対象市場(日本株 / 米国株 / ETF / 暗号資産)と手数料
- 自動売買の約款上の可否、API 利用料

### 投資ロジック決定がシステムに与える影響
- 判断サイクル(日次 / 週次)→ スケジューラ設計と LLM コスト
- 対象銘柄数 → データ API のコストとレート制限
- ロジックの種類(モメンタム / バリュー / ニュースドリブン等)→ 必要データソースが変わる
- ※スキャルピング等の高頻度戦略は本アーキテクチャでは非対応

## 10. リスク・免責事項

- LLM の判断は誤る(ハルシネーション・過剰取引バイアス)。ガードレールと少額検証を必須とする
- SNS 上の「AI で市場に勝った」系の報告は生存者バイアスが強く、再現性は保証されない
- 元本割れリスクは発注者が負う。本システムは利益を保証しない
