## 1. 参照元ポストの内容(確定)

Claude を使ってクオンツボットを開発し、Polymarket(予測市場)で +$218,425 を獲得した事例。

| 項目 | 値 |
|------|-----|
| 対象 | Polymarket の BTC/ETH/SOL「5分足の上下」予測マーケット等 |
| 初期資金 | 約 $304.8K(約 4,500 万円) |
| 運用期間 | 64 日 |
| 損益 | +$218K(ROI 約 +71.7%) |
| 取引回数 | 48,018 回(約 31 回/時) |
| 勝率 | 52% |
| 戦略 | オッズの再調整(repricing)が完了する前の歪みに先回りして入り、小さなエッジを大量回数で積み上げる(レイテンシ/ミスプライシング・アービトラージ) |

**本質的な構造(要件に直結する 2 点)**
1. **Claude はボットの「開発者」であり、リアルタイムの売買判断はしていない。** 31 回/時・秒単位の執行に LLM 推論は速度・コスト的に入れられない。売買はコード化された決定論的ロジックが行い、Claude は戦略の実装・分析・改善サイクルに使う。
2. **エッジの源泉は「現物価格の動きに対する Polymarket オッズの調整遅れ」**。したがってシステムの核は、現物価格のリアルタイム取得 → フェア確率の推定 → オッズとの乖離検知 → 高速執行、のパイプラインである。

## 2. 目的・ゴール

Polymarket 上の短期予測マーケットにおいて、オッズの調整遅れを検知し、小さな期待値エッジを高頻度で積み上げる自動売買ボットを構築する。Claude は開発・バックテスト・ログ分析・パラメータ改善のループに組み込む。

**段階ゴール**
1. Phase 1: シャドーモード(実発注なし)で「検知したエッジが実際に実現したか」を 2〜4 週間計測し、理論エッジ > 手数料+スリッページ を確認
2. Phase 2: 少額実資金でのライブ稼働(1 取引あたり数ドル〜)
3. Phase 3: Kelly 基準ベースのサイズ拡大(Phase 2 実績に基づき判断)

## 3. 重大な前提確認(Go/No-Go 判断事項)

**着手前に必ず確認が必要。ここが No なら本プロジェクトは方針転換する。**

1. **法規制(最重要)**: Polymarket は予測市場であり、日本居住者の利用は (a) Polymarket の利用規約・ジオブロック対象か、(b) 日本の賭博罪(刑法185条)に抵触するおそれがないか、の 2 点で法的グレー〜リスクあり。発注者の居住国・リスク許容度の確認が必須。日本居住で法的リスクを取らない場合の代替案は §10 参照。
2. **資金規模**: 参照事例は約 $300K 投入。この戦略は「1 回あたりの利幅が小さい×回数」型のため、少額資金だとインフラ・手数料コストを上回れない可能性が高い。投入可能額の確認が必要。
3. **エッジの持続性**: 公開・拡散された時点でエッジは縮小しているのが通例。「同じ戦略の再現」ではなく「同じ枠組みで自分のエッジを探す」プロジェクトである、という期待値の合意が必要。

## 4. システム構成

```
┌─ 開発・改善ループ(Claude の役割)──────────────────┐
│ 戦略実装 / バックテスト / 取引ログ分析 / パラメータ改善提案 │
└──────────────┬───────────────────┘
               ▼ コードとして反映
┌─ ランタイム(決定論的・低レイテンシ / LLM 不使用)─────┐
│ ① 価格フィード: 現物価格 WebSocket(Binance/Coinbase 等)   │
│ ② マーケットフィード: Polymarket CLOB WebSocket(板・オッズ)│
│ ③ シグナル: フェア確率推定 ↔ 現在オッズの乖離検知          │
│ ④ サイジング: Kelly 分数 + 上限キャップ                    │
│ ⑤ リスクゲート: コード強制のガードレール(発注前チェック)  │
│ ⑥ 執行: Polymarket CLOB API 発注・約定管理                 │
│ ⑦ 記録・監視: 全シグナル/発注/約定を DB へ、異常時即通知    │
└──────────────────────────────────┘
```

**設計上の決定事項**
- **ホットパス(検知→発注)に LLM を入れない。** 目標レイテンシは検知から発注まで 1 秒未満。LLM は夜間・週次の分析改善サイクルのみ。
- リスク制約(1 取引上限、日次損失上限、総エクスポージャ上限、取引頻度上限)は**コードで強制**。違反時は発注拒否+通知。
- ウォレットは**ボット専用に分離**し、運用上限額のみ入金。秘密鍵はシークレット管理サービスで保管。
- すべてのシグナル(見送り含む)を記録し、シャドーモードとライブの成績を同一フォーマットで比較可能にする。

## 5. 機能要件

| # | 機能 | 内容 | 優先度 |
|---|------|------|--------|
| F-1 | 現物価格フィード | BTC/ETH/SOL 等の現物価格を WebSocket でリアルタイム取得(冗長化: 2 取引所以上) | 必須 |
| F-2 | Polymarket フィード | 対象マーケットの板・オッズ・約定を CLOB WebSocket で取得。対象マーケットの自動発見(5分足市場は次々に生成されるため) | 必須 |
| F-3 | フェア確率推定 | 現物価格・残り時間からマーケットの「あるべき確率」を推定(初期はシンプルなモデル、改善はデータ駆動) | 必須 |
| F-4 | エッジ検知 | 推定確率と現在オッズの乖離が閾値(手数料+スリッページ+マージン)超で候補化 | 必須 |
| F-5 | サイジング | Kelly 分数(例: 1/4 Kelly)+ 絶対額キャップで注文サイズ決定 | 必須 |
| F-6 | リスクゲート | 上限/損失/頻度/エクスポージャの発注前チェック。日次損失上限到達で自動停止 | 必須 |
| F-7 | 執行 | 指値発注、部分約定・失効の管理、決済(settle)確認 | 必須 |
| F-8 | シャドーモード | 実発注せず「発注していたら」の仮想約定と実現損益を記録(Phase 1) | 必須 |
| F-9 | 記録 | 全シグナル・全発注・全約定・PnL を DB 保存。日次で Claude が分析可能な形式にエクスポート | 必須 |
| F-10 | 監視・通知 | 稼働死活、日次損失、ガードレール発動、フィード断を即時通知(Slack/LINE)。日次 PnL サマリ | 必須 |
| F-11 | 緊急停止 | ワンアクションのキルスイッチ(全注文取消+新規停止) | 必須 |
| F-12 | 改善ループ | 取引ログを Claude に渡し、勝敗要因分析・閾値/モデルの改善案を生成する定期ジョブ(適用は人間承認制) | 推奨 |
| F-13 | バックテスト | 収集した履歴データでロジック変更を事前検証 | 推奨 |

## 6. 非機能要件

| # | 項目 | 要件 |
|---|------|------|
| N-1 | レイテンシ | シグナル検知→発注 1 秒未満。実行環境は取引 API に近いリージョンのクラウド常駐プロセス |
| N-2 | 可用性 | 24/365 稼働(クリプト市場は無休)。プロセス監視・自動再起動。障害時は「新規停止・既存ポジションは通知」に倒す |
| N-3 | セキュリティ | ウォレット秘密鍵・API キーはシークレット管理。ボット専用ウォレットに運用上限額のみ。リポジトリに秘密情報を含めない |
| N-4 | 監査性 | 全判断が時系列で追跡可能。オンチェーン取引はウォレットアドレスで第三者検証可能 |
| N-5 | コスト管理 | インフラ+データ+ガス代(Polygon)+LLM の月次上限とアラート |

## 7. 必要な準備(すべて)

1. **Polymarket / ウォレット関連**
   - 居住国での利用可否の法的確認(§3-1。**最優先・着手前**)
   - Polymarket アカウント(KYC 要否確認)と CLOB API キー
   - ボット専用 Polygon ウォレット作成、USDC の入金経路(国内暗号資産交換業者 → 送金)の確保
2. **開発・実行環境**
   - Anthropic API(開発・分析ループ用)
   - 24/365 稼働のクラウド環境(VPS/コンテナ)、監視(死活・アラート)
   - 本 GitHub リポジトリ・CI
3. **データ**
   - 現物価格 WebSocket(Binance/Coinbase 等、無料枠で開始可)
   - Polymarket 履歴データの収集基盤(バックテスト用。Phase 1 の稼働自体がデータ収集を兼ねる)
4. **資金・リスクルール**
   - 投入資金額と損失許容上限(全損許容額)の決定
   - リスクパラメータ初期値(1 取引上限、日次損失上限、総エクスポージャ上限、Kelly 分数)
5. **税務**
   - 予測市場・暗号資産の損益は日本では雑所得(総合課税)となる見込み。取引数が数万件になるため損益計算の自動集計を F-9 に含める
6. **運用体制**
   - 通知先(Slack/LINE)、週次レビュー(人間+Claude 分析)の運用ルール、緊急停止手順

## 8. 開発フェーズ

| Phase | 内容 | 完了条件 | 期間目安 |
|-------|------|----------|----------|
| 0 | 法的確認・アカウント/ウォレット準備・資金決定 | Go/No-Go 判断(§3)完了 | 1〜2 週間 |
| 1 | フィード+シグナル+シャドーモード実装(F-1〜F-4, F-8〜F-11) | 2〜4 週間のシャドー計測で「理論エッジ>コスト」を確認 | 実装 3〜5 週間+計測 2〜4 週間 |
| 2 | 執行系実装・少額ライブ(F-5〜F-7) | シャドーとライブの成績乖離が説明可能な範囲。ガードレール発動テスト合格 | 2 週間+検証 1 ヶ月 |
| 3 | サイズ拡大・改善ループ本格化(F-12, F-13) | Phase 2 の実績評価に基づき判断 | 継続 |

**Phase 1 でエッジが確認できなければ Phase 2 に進まない(損切りの明文化)。**

## 9. リスク・免責事項

- **エッジ消失リスク**: 公開された戦略は模倣者の流入で急速に劣化する。参照事例と同等の成績は期待しない
- **法的リスク**: §3-1 のとおり。発注者の判断と責任で Go/No-Go を決定する
- **オペレーショナルリスク**: フィード断・API 障害・ガス詰まり・ウォレット侵害。ガードレールと専用ウォレット分離で限定する
- **参照事例の信憑性**: ダッシュボード画像は演出の可能性がある。ウォレット(0x50f7…)のオンチェーン実績は Polymarket プロフィールで着手前に検証する
- 元本割れ(全損含む)リスクは発注者が負う。本システムは利益を保証しない

## 10. 代替案(日本居住で Polymarket の法的リスクを取らない場合)

同じ「調整遅れ×高頻度×小エッジ」の枠組みを、合法性が明確な場に適用する:

- **A. 国内暗号資産取引所間のアービトラージ/マーケットメイク**(bitFlyer・GMO コイン等の API): 合法・円建て。競争は激しいがインフラはほぼ流用可能
- **B. 海外デリバティブ取引所(Bybit 等)の資金調達率・ベーシス戦略**: 中頻度でエッジが構造的。ただし国内無登録業者の利用リスクは別途確認
- **C. 株式(kabu ステーション API 等)でのイベントドリブン**: 完全合法だが「高頻度小エッジ」型は個人では困難。v0.1 の構成に近い日次サイクル型になる
